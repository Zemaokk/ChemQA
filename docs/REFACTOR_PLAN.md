## 1. 项目定位

面向电化学研究者，构建一个能够从指定文献库中检索证据、回答科研问题，并让使用者核查答案依据的问答系统。

暂定英文名称：**ChemQA: Evidence-Grounded QA for Electrochemistry Literature**。

核心目标是：**证据可追溯、效果可验证、流程可复现**。

在申请材料中，ChemQA 拟作为第二个 main project，与第一项目 InferGate 形成互补：InferGate 侧重软件系统工程；ChemQA 侧重领域需求、文献处理、信息检索、LLM 应用与实验评估。最终表述以实际实现和验证结果为准。

## 2. 用户与使用场景

主要用户是需要阅读、比较和核查电化学文献的研究者。初期从指定的本地文献库出发，明确语料覆盖范围。

优先支持以下问题：

- **事实查找**：某篇论文采用了什么电解液、反应条件或表征方法？
- **条件与数值查询**：某项性能数据对应什么实验条件？
- **文献比较**：不同研究在催化剂、反应条件、性能或证据方面有什么差别？
- **证据判断**：现有文献片段是否足以支持某个机制解释或回答某个问题？

回答需要区分不同反应体系、实验条件和证据层级。类比、解释或推断应明确标注，不能直接写成原文结论。

“证据不足”指当前文献库或当前检索结果不足以回答，不能扩大为“整个领域没有相关研究”。系统还应区分检索失败、文献覆盖不足和模型/API 失败。

以下为 2026-10-06 对当前仓库的检查结果，不代表已重新运行完整问答流程：

- 3,200 个处理后的文本块，以及 3,200 个 384 维向量。
- 已有 PDF 提取、文本分块、Sentence Transformers 编码、向量检索、DeepSeek 回答生成及 Markdown 输出流程。
- 保留了同一组 10 个问题的带检索回答与直接模型回答，以及两组各 15 个示例答案。
- 已有引用标记统计及查询—文本块相似度热力图。

当前向量检索实际采用 JSON 保存索引、NumPy 计算点积并排序；README 中的 FAISS 描述与实现不一致。

这些材料支持“实现了领域文献检索增强问答原型”的表述。目前尚不足以证明准确率提升、幻觉减少或引用正确性。已有答案是历史运行材料，不能直接当作受控实验结果。

## 4. 最终目标与验收方向

| 目标 | 预期行为 | 验收证据 |
|---|---|---|
| 证据可追溯 | 关键事实关联到具体文献、页码及原文片段；引用对应正确 | 可核查的回答示例、引用映射验证、人工抽查 |
| 效果可验证 | 在固定问题集上比较基线与改进，说明收益和失败情况 | 标注数据、评估定义、实验配置、结果与错误分析 |
| 流程可复现 | 其他人可以按说明构建索引、运行问答并复现实验 | 安装说明、示例数据、运行入口、配置及实验记录 |

不预先承诺准确率或性能提升幅度。改进是否有效由实验决定；无明显收益的方案也应记录结果与原因。

## 5. 主流程与开发范围

主流程：

**文献处理 → 检索 → 证据组织 → 回答生成 → 引用核查 → 评估**

这一轮的必要范围：

- 文献与文本块的身份、来源和位置记录。
- 尽可能保留化学符号、实验条件及数值信息的文本处理。
- 定义清楚、可比较的基础检索流程。
- 明确的上下文序列化与证据编号。
- 基于证据的回答，以及证据不足时的适当说明。
- 正确的引用对应关系和可核查输出。
- 小规模领域评估集、基线实验和错误分析。
- 可复现的配置、依赖、命令入口与文档。

可选扩展由实验或使用需求决定：混合检索、重排、更换 embedding 模型、替换索引存储方式、简单网页演示。

多智能体、自动实验设计、模型微调及复杂部署暂不纳入本轮计划。FAISS 等工具也不作为必须引入的目标。

## 6. 评估设计方向

先准备少量人工标注问题，帮助开发过程中判断改动是否有效；逐步扩充到约 40–60 个问题。该数量是工作规模建议，不是统计充分性的保证。

问题集应覆盖单篇事实、多篇比较、具体数值与条件、证据不足，以及容易混淆的反应体系。每题记录问题、相关文献、证据位置、回答要点及是否可由当前语料回答。

划分用于开发的问题和用于最终验收的问题；调整阈值或检索方案时使用开发部分。预留问题的最终结果不能反复用于调参后仍称为独立验收。

候选比较方案：

1. 直接调用 LLM，不提供检索上下文。
2. BM25 检索加回答生成。
3. 稠密向量检索加回答生成。
4. 一种有明确动机的改进方案，在前三项建立后确定。

端到端比较应尽量固定生成模型、回答要求和生成参数，并记录提示词、上下文预算、API 使用及重试情况。不同方案必要的输入差异应说明。检索效果与回答效果分别评估。

| 评估方面 | 要回答的问题 |
|---|---|
| 检索 | 标注的相关文献或证据是否进入结果？排名是否合适？ |
| 回答事实 | 关键事实和数值是否正确，条件是否完整？ |
| 证据支持 | 回答中的事实性主张是否受到所引原文支持？ |
| 引用对应 | 引用能否定位到正确文献与片段？ |
| 证据不足 | 是否正确说明不足，是否把其他体系误当作直接证据？ |
| 成本与耗时 | 每次问答消耗多少 token、费用和时间？ |

具体指标、评分规则和重复运行次数在评估问题启动时确定。引用标记出现率、答案长度、上下文使用比例均不能直接代表答案质量。

领域标注应记录标注者和规则。尽可能由另一位研究者复核部分题目，并保留分歧。自动评分可以辅助，但需要人工抽查。

## 7. 逐项推进方式

**一次只解决一个明确问题。** 阶段是方向说明，不是一次性批量修改的授权。

每个问题按以下顺序推进：

1. 描述当前行为、具体例子及其对整体目标的影响。
2. 在实现前确定验收标准。
3. 讨论方案、取舍与本次边界。
4. 实现当前问题所需的改动。
5. 进行有意义的验证，记录结果和剩余限制。
6. 完成本项总结，再进入下一个问题。

一项改动可以涉及多个文件，但必须服务于同一个问题。发现其他问题时加入待办，不顺手扩展本次范围。若存在阻塞依赖，先说明依赖并重新界定本项范围。

建议为每个启动的问题留下简短记录：问题、验收标准、方案、实际改动、验证、未解决事项。问题的实现方式和协作分工在启动时确定。

整体推进分为三个阶段：

- **基础正确性与复现**：逐项修复数据身份、引用、文本处理、配置和运行问题，同时准备少量评估样例。
- **评估与有依据的改进**：建立基线，定位失败原因，再逐项尝试改进。
- **展示与申请材料**：整理可运行演示、技术报告、结果及符合证据的 CV 描述。
